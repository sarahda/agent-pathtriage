\section{Conclusion}
\label{sec:conclusion}

Managed agent platforms put several identities in one account. The question
that matters is not what one agent can reach, but what it can reach by going
through another agent. That does not fit a single identity analysis. We stated
it as a set difference, implemented it, and ran it over public AWS
deployments.

In a live account, an attacker holding the vendor's own managed policy took
over a sibling agent and ran code under the victim's role. The only thing that
decided the outcome was the victim role's name. A role built identically and
named differently was refused, and the name that succeeded was one the
vendor's own console produces. The takeover also outlived the attacker: with
every policy detached from the attacker principal, the operator's own call
still returned the planted code's answer. Replacing what an agent runs cannot
avoid \iam{iam:PassRole}, because one API call decides the code and the
identity together.

The conditions for that are already present in public code. Where more than
one agent exists, \nSharedRoleRuntimes of \nMultiAgentRuntimes run every agent
under a single role. That makes the escalation unnecessary, and it leaves the
account unable to tell its agents apart. A further \nBlocked takeover
candidates are held back by one permission, and it is the same permission in
every case.

What the corpus does not contain is a finished path. We found \nChainsFound,
which supports an upper bound of \chainBound and nothing stronger. The
weight of the measurement is not in that rate. It is in the distance being
short, and the same, everywhere it was measured.

Set against the published accounts of this platform, what this paper adds is
narrow: a route whose effect outlives the attacker's
access, a control that locates the gate in the name of a role rather than in
its ownership, and a count of how often the starting position those accounts
assume is already present in deployments people publish.

The defence follows from that: give each agent its own execution role, and
treat \iam{iam:PassRole} over an agent's execution role as a grant of that
agent's permissions to whoever holds it.


\subsection{How far each question is settled}

\textbf{RQ1} is settled. The predicate in Equation~\ref{eq:esc} and the
delegation rules in Section~\ref{sec:approach} decide cross-agent escalation
from template source alone, with no running account. On IAM-Vulnerable they
recover all \nIVPaths of the planted delegation paths, where a check that
reads one identity at a time recovers none of them.

\textbf{RQ2} is answered as a bound, not as a rate. No complete path appears
in the \nChainDenominator units the chain analysis covered, which supports
\chainBound and nothing stronger. The preconditions are a separate finding
and a firmer one: \nSharedRoleRuntimes of \nMultiAgentRuntimes multi-agent
deployments run every agent under one role, and \nBlocked takeover candidates
across \nBlockedConfigs projects are held back by the same single permission.
The corpus is public infrastructure as code and private deployments may differ,
which Section~\ref{sec:limitations} sets out.

\textbf{RQ3} is settled for the account tested, and only for it. Two victim
roles built identically and differing only in name gave opposite outcomes, so
the gate is a match on the role's name rather than any statement about whose
role it is. One account is one configuration, and Section~\ref{sec:limitations}
says what a single trial does not establish.
